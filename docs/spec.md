# 体育祭サイト「長田すぎて滅！青春爆裂愛してる」仕様書

> **ステータス**: MVP 実装済み（表画面はモック v2「爆裂」を移植、学年別ヒート・進行遅延・得点公開・出場競技表の静的配信に対応。Supabase 接続と実機確認が残り） ・ **作成日**: 2026-08-30 ・ **最終更新**: 2026-09-13
> **読者**: 実装するエージェント（必要に応じて人間）。背景は [../README.md](../README.md)、作業規約は [../AGENTS.md](../AGENTS.md)、他の設計は [README.md](README.md)（docs の索引）。

実装の**契約書**。各機能の「受け入れ条件」が合格ラインで、AGENTS.md の検証ループで照合する。仕様を変えたら同期規約に従いこのファイルと関連 docs を更新する。

---

## 1. 概要

- **一言コンセプト**: 体育祭の公式情報サイト＋サイト内ポイントだけで遊べる隠しカジノ風ベット機能
- **ターゲット**: 全校生徒（3学年・8チーム、招集案内は最大960人規模）＋実行委員（管理者）
- **チーム構成**: 学年をまたいだ色別対抗、全体で8チーム

> 詳しい背景は ../README.md（重複させない）。

## 2. 機能一覧

### ✅ MVP

#### 機能1：組み合わせ・プログラム表示
> 見た目と構成の出典は `docs/mockup/体育祭サイト モック v2 爆裂.dc.html`（[DESIGN.festival.md](DESIGN.festival.md)）。種目データの出典は R8 演技台帳（12 プログラム）。

- [x] トップページ（`/`）でプログラム 12 枚（番号・状態タグ 終了/進行中/次/予定・名称・英語名・時刻・場所）と TIMETABLE が閲覧できる（ログイン不要）
- [x] プログラムのカードを押すと詳細（ルール要約・対象・集合場所・持ち物・組み合わせ・ヒートごとの着順）がモーダルで開き、Esc／✕で閉じる
- [x] 実行委員が種目データを登録・編集すると、トップページの表示に反映される（30 秒ごとの自動再取得）
- [x] 実行委員が「進行の遅延・前倒し」で時刻を動かすと、トップの時刻・状態タグ・カジノの締切カウントダウンに反映される（機能8）

#### 機能2：得点・順位の表示（当日は非公開、閉会式で公開）
> モック v2 の方針「当日の途中経過は非公開。閉会式の総合成績発表で一斉に出す」を採用。

- [x] 得点が未公開の間、トップの「爆裂 8 CLASSES」には 8 クラスの色と名前だけを表示し、得点・順位を一切出さない（「得点は最終集計後に公開」と明記）
- [x] 実行委員が `/admin` で「得点を公開」すると、トップの同じ枠に得点と順位が表示される。「非公開に戻す」で再び隠せる
- [x] 管理画面では公開状態に関わらず現在の得点・順位を常に確認できる（「得点」タブ）
- [x] 実行委員が種目のヒート（学年別レースなど）ごとに着順を入力すると、順位点から得点が計算されて合計に反映される。順位点の無い種目（玉入れ・棒引き）は得点を直接入力する
- [x] ヒートの結果を確定すると、対応する Market（ベット対象）が自動的に `settled` になる（配当付与と利子加算も同時）

#### 機能3：学籍番号入力・マイページ（認証なし）
> 表側に「ログイン」は無い。学籍番号は本人確認ではなく**検索キー**で、他人の学籍番号を入れて他人の出場競技を見るのも想定内（友人の集合場所を確認する用途）。セッション・パスワード・DB 照合は行わない。カジノの認証（機能5）とは完全に別系統。

- [x] `/login` で学籍番号のみを入力すると `/me?id=<学籍番号>` に遷移する（名前・パスワードは求めない）
- [x] 学籍番号の形式が不正（空・数字以外）な場合は入力欄にエラーを表示して遷移しない。存在チェックは行わない（全角数字は半角に正規化）
- [x] `/me` には出場競技（機能4b）と招集案内（機能4）だけを表示する。ポイント残高・借金・ベット履歴はカジノ側（`/casino`）にのみ表示し、表側には一切出さない（カジノの存在を表側で露出させない）
- [x] `/me` の黒帯に学籍番号と、学年・組（学籍番号から導く）を表示する。名簿にあれば「2年1組・1組 紅蓮・サンプル生徒04」のようにチーム名と氏名も加わる

#### 機能4：招集案内検索
- [x] 実行委員が `/admin` から招集案内CSV（学籍番号・種目名・集合時間・場所、任意で補足タグ）をアップロードできる
- [x] `/me?id=<学籍番号>` の「自分の招集案内」に、該当する招集案内（複数件あれば全件）を集合時間・種目・場所・補足タグ（ゼッケン着用など）の形で表示する
- [x] 該当する招集案内が無い学籍番号には「現在、招集案内はありません」と表示される
- [x] 「出場種目」に、招集案内の種目名と一致する種目を番号・時刻つきで一覧する
- [x] 「種目別 招集案内」で全種目を 区分（すべて/式典/トラック/フィールド/部活動）で絞り込み、種目を押すと 招集開始目安・集合場所・持ち物・対象・3D会場図・集合と競技位置への誘導矢印が開く
- [x] `/me` で別の学籍番号を入力し直して他の人の招集案内を見られる

#### 機能4b：出場競技表（DB を使わない静的データ）
> 「自分が何に出るのか」は当日いちばん多く引かれる情報なので、DB を通さず**静的データ**で返す。元データは実行委員が配る CSV（`data/学籍番号別出場競技.csv`）で、ビルド時に `src/lib/festival/entries.data.ts` へ変換して JS バンドルに同梱する。実行委員が随時更新する招集案内（機能4）とは別系統で、こちらは CSV 差し替え → ビルド → デプロイで反映する。

- [x] `data/学籍番号別出場競技.csv`（見出し `学籍番号,出場競技`、1 セル内は全角縦棒 `｜` 区切り）から `npm run entries` で静的データを生成する。`npm run dev` / `npm run build` の前に自動で走る
- [x] 生成時に 見出し不正・学籍番号の重複・学籍番号の形式不正・空の出場競技・引用符つき CSV・**区切りが半角の `|` になっている**行を検出したらビルドを失敗させる（差し替えミスに気づけるようにする）。`競技名（枠）` の形でない行は警告だけ出して通す（枠は空欄で表示）
- [x] `/me?id=<学籍番号>` の「自分の出場競技」に、CSV の並び順で 競技名（`大縄跳び 前半`）と自分の枠（`16人目`・`第1走者`）を表示する。このセクションは DB にアクセスしない
- [x] 「自分の出場競技」「自分の招集案内」「出場種目」の 3 セクションには同じ種目名が並ぶので、見出しの下にそれぞれの役割（自分の枠／集合時間・場所・持ち物／プログラム番号と開始予定時刻）を一言で書き分ける
- [x] 出場競技表に無い学籍番号には「この学籍番号は出場競技表にありません」と表示する（招集案内 0 件の場合とは別の文言）
- [x] 「自分の出場競技」は DB の応答を待たずに描画され、招集案内など DB 由来のセクションは後から Suspense で流し込まれる
- [x] 黒帯の学年・組は学籍番号（4 桁 = 学年1桁・組1桁・出席番号2桁）から出すので、名簿が未アップロードでも表示される。名簿があればチーム名・氏名が後から加わる
- [x] 「自分の出場競技」の下に出場競技表の版（生成元 CSV の SHA-256 先頭 8 桁）を出し、どの CSV が反映されているか確認できる

#### 機能4c：3D集合案内（DB不要・マイページ内）

資料・未確定事項・連携方法は [ground-guide/README.md](ground-guide/README.md)。`/me` の出場競技カードと種目別招集案内の中で3Dを展開する。独立した `/ground-guide` も維持する。

- [x] `/ground-guide?id=<学籍番号>&event=<競技名またはキー>` で、DBや外部地図APIを使わず静的出場データと競技配置を表示する
- [x] 回転・拡大縮小・真上表示できる3Dモデルと、出発→集合→競技の2段階の矢印を表示する。glTF形式のモデルを保存できる
- [x] 種目別案内は競技全体の集合区分と全区分の通し再生を示し、出発地・学年組・走順入力・GPS・個人経路を出さない。個人案内は同じ全区分を表示し、自分の区分を色と文字で強調する
- [x] 全12プログラムを選択でき、リレーは学年・組・走順から招集側とコースを区別する。個人の棒番号や玉入れのコートを推測しない
- [x] 航空写真と資料図の上下反転を合わせ、本部側をモデルの下に統一する。実測でない寸法・通路は概略と明示する
- [x] 自分の組の生徒席を初期出発地点とし、手動で変更できる。テントは左1年・奥2年・右3年の外周曲線に沿って接線方向に配置し、集合・競技へのトラック横断を許可した直接の矢印を表示する。GPSは明示操作時だけ取得し、2点位置合わせ後に現在地からの矢印を更新する。位置合わせ前は階段への直線距離だけを表示する
- [x] GPS拒否・取得失敗・範囲外・精度不足は手動案内を使える。監視停止と離脱時の解除ができ、位置情報を送信・永続保存しない
- [x] R8.zipから氏名を含まない配置図と要約だけをdocsに保存し、資料の時刻不整合・未実測GPS較正点を明記する

未決定事項：本番用GPS較正2点と実測位置の現地確認、玉入れ・騎馬戦の集合時刻の資料不整合、個人と棒番号・玉入れコートの対応。画面に要確認を表示し、不明な精密位置・時刻を確定値にしない。

#### 機能5：隠しカジノへの入場（カジノ独自の認証）
> 表側の学籍番号入力とは無関係。カジノ口座は `/casino/enter` で学籍番号＋パスワードにより作成・認証し、入場後はサーバーが発行する署名付き Cookie セッションで本人を特定する。Route Handler はこのセッションから学籍番号を取り、リクエスト本文の学籍番号は信用しない。

- [x] トップページのフッターの「79」を 1.4 秒以内に 5 回連続タップすると、`/casino/enter` の筐体に切り替わり、液晶内でモックv3と同一の19行のCLI起動ログを表示する。入力行は1文字/46ms、出力行は約7分割/18ms、初期待機1000ms。タップごとに文字色が変わる
- [x] 初回は学籍番号＋パスワード（新規設定）＋ニックネームを入力するとカジノ口座が作成され、`/casino` に入場する（初期ポイント1000pt付与）。学籍番号は生徒名簿（STUDENT）に存在するものに限る
- [x] ニックネームは 1〜12 文字（前後の空白・改行・制御文字は不可）で必須。要件を満たさないと `INVALID NICKNAME` が表示され口座は作られない。重複は許可する（順位表では学籍番号も併記する）。作成後の変更機能は無い
- [x] 2回目以降は学籍番号＋パスワードの入力で `/casino` に入場できる
- [x] パスワードが誤っている場合はエラーが表示され入場できない（口座の有無は明かさない）
- [x] 未入場（セッション無し）の状態で `/casino` 配下や `/api/casino/*` にアクセスすると `/casino/enter` に誘導される（API は 401）

#### 機能6：カジノ内ベット機能（パリミュチュエル方式）
- [x] `/casino` で「体育祭全体の優勝チーム」と「種目（ヒート）ごとの勝者」の両方に対してポイントを賭けられる（学年別レースは「女子6×100mリレー 2年」のようにヒート単位の Market）
- [x] 1つの Market 内で複数チームに分散してベットできる（例：1組に500pt、3組に300pt）
- [x] 締切前の Market には、賭けられている金額から計算した見込み倍率がリアルタイムに表示される（計算方法は [data-model.md](data-model.md) を参照）
- [x] 締切（`deadline`）前であれば、確定済みの自分のベットを取り消せる（取り消すと賭けたポイントは全額 `points_balance` に戻る）
- [x] 締切（`deadline`）を過ぎた Market には新規ベット・取り消し・追加ができない
- [x] `points_balance` を超える金額はベットできない（不足分は先に「借りる」機能でポイントを補う必要がある）
- [x] 実行委員が結果を確定すると、的中した生徒には配当が自動計算・付与され、外れた生徒はベットしたポイントが没収される
- [x] 結果発表の際にカジノらしい演出（液晶上のリール回転→着順ロック→HIT/MISS 表示と効果音）が表示される。演出は CSS keyframes と WebAudio で実装し、外部ライブラリは使っていない
- [x] 自分のベットが的中していた場合は、リールが止まった直後に液晶全面の的中演出（▲ HIT ・ 的中 ▲／払戻額／実効倍率／的中した対象／紙吹雪）が 3.4 秒表示され、タップ・キー・ENTER で閉じられる（モック v3 最新版）。紙吹雪は Canvas 2D で描き、依存は増やさない。払戻・倍率の集計は `src/lib/casino/odds.ts` の `summarizeHits`（単体テストあり）

> データは `src/lib/db/`（Supabase 未設定時はメモリ実装＋開発用シード）から取得し、生徒はカジノ入場セッションで特定する。

- [x] 前画面（`/casino`）で選択した競技名が表示される
- [x] 本画面には競技一覧・Market一覧を表示しない
- [x] 前画面へ戻る操作が存在する（‹ EVENTS／BACK／Esc）
- [x] 残高と借金額が常時確認できる
- [x] 締切までの時間またはMarket状態（BET CLOSE／CLOSED／SETTLED）が確認できる
- [x] race競技では単勝・複勝・三連単を切り替えられる（field・overall・custom は賭式タブを出さない）
- [x] 単勝・複勝では8チームのオッズを一覧確認できる
- [x] 賭けがない対象の倍率は `―` と表示される
- [x] チームを選択するとBet Slipが展開する
- [x] 1pt以上の整数だけを賭けられる（サーバー側でも検証）
- [x] 残高を超えるベットを確定できない（サーバー側でも検証）
- [x] ベット前に対象・金額・見込み払戻額を確認できる
- [x] ベット成功後に残高が更新される
- [x] 同じMarketへ続けて追加ベットできる
- [x] 三連単では1・2・3着を個別指定できる
- [x] 三連単で同一チームを複数順位に指定できない（UI で選択不可＋サーバーで拒否）
- [x] 三連単では選択中の組み合わせだけ倍率を表示する
- [x] Custom Marketでは二択専用UIを表示できる
- [x] 締切前の自分のベットを1件単位で取り消せる
- [x] 締切後は新規ベット・追加・取消ができない（サーバー側でも検証）
- [x] 通信エラー時に入力内容を保持したまま再試行できる（CONNECTION ERROR → RETRY）
- [x] スマートフォンから主要操作を問題なく行える（390px 幅のヘッドレス Chrome で全画面の横スクロール無しを実測。実機での確認は未実施）

#### 機能7：借金（クレジット）・利子システム
- [x] `/casino` の F2 CREDIT（`/casino/credit`）に「借りる（ADVANCE）」があり、金額を指定してポイントを借入れできる（`points_balance` が加算され、同額が `debt_amount` にも加算される）
- [x] 1回の借入れ上限は500ptで、超える金額は借りられない（サーバー側で検証）
- [x] 借入れの合計上限（`debt_amount` の上限）は設けない
- [x] いずれかの Market が結果確定（`settled`）するたびに、その時点で `debt_amount` が0より大きい生徒全員に10%の利子が加算される（`debt_amount = debt_amount × 1.1`、端数切り捨て。計算方法は [data-model.md](data-model.md) を参照）
- [x] `/casino` 配下の全画面に現在の `points_balance` と `debt_amount` が常に表示される（表側の `/me` には表示しない）
- [x] 「返済（REPAY）」でいつでも任意の額を `points_balance` から `debt_amount` に充当できる（返済額は `points_balance` 以下かつ `debt_amount` 以下）。最終精算後は借入・返済とも拒否される

#### 機能8：実行委員管理画面
- [x] `/admin/login` で実行委員としてログインできる（生徒ログインとは別のアカウント体系。Supabase 設定時は Supabase Auth、未設定時は環境変数の資格情報）
- [x] `/admin` から種目・チームの登録、得点・勝敗結果（着順）の入力、招集案内CSV・生徒名簿CSVのアップロード、Marketの作成・締切変更・即時締切・結果確定操作ができる
- [x] 種目にヒート（1年/2年/3年 など）を登録でき、結果入力と Market 作成はヒート単位で行える
- [x] 「進行の遅延・前倒し」で、種目ごとの「−1分／+1分」（その種目以降がまとめて動く）、「全体 −1分／+1分」、「定刻に戻す」ができ、トップの時刻とカジノの締切に反映される
- [x] 「得点を公開」「非公開に戻す」で表側の得点表示を切り替えられる。管理画面には常に得点板が出る
- [x] 式典・部活動の種目（開会式・部行進など）は結果入力の対象外（Market を紐づけた場合だけ表示）
- [x] 実行委員セッションが無い状態で `/admin` にアクセスすると `/admin/login` に戻される（カジノのセッションでは入れない）
- [x] `/admin` から「最終精算」を実行すると、全生徒の `points_balance -= debt_amount` が確定し、以降の借入れ・返済ができなくなる（2 回目以降の実行は何もしない）

#### 機能9：最終順位ランキング公開
- [x] `/admin` の「最終精算」実行後、`/ranking` で純資産（`points_balance - debt_amount`）順に個人のランキングが全体公開される。表示名は口座作成時のニックネーム（ニックネームの無い旧口座は名簿の氏名、名簿にも無ければ学籍番号）で、学籍番号を併記する。名簿の氏名は出さない

### 構成・設計判断（inline）

| 判断 | 選択 | 理由 | 代替 |
|---|---|---|---|
| DB・認証 | Supabase（Postgres + Auth） | 無料枠で完結し、生徒960人規模の読み取り・カジノの数十人同時アクセスに十分。DBを分ける必要がない | Firebase（Firestore は関係データ・集計が弱く、パリミュチュエル計算に不向き） |
| 認証の分離 | 表側は認証なし（学籍番号は検索キー）／カジノは学籍番号＋パスワードの独自認証（署名付き Cookie セッション）／実行委員は Supabase Auth | 表側は「自分や友人の出場競技と場所を見る」用途なので本人確認が不要で、他人の分も見られる方が都合がよい。カジノはポイントを扱うため本人特定が必須。Supabase Auth はメール前提なので生徒向けには使わず、実行委員にだけ使う | 表側も学籍番号＋名前でログイン（なりすまし防止にならず、手間だけ増える） |
| 永続化の抽象 | `src/lib/db/repository.ts` のインターフェース＋メモリ実装（開発）／Supabase 実装（本番、PostgREST を fetch で直接叩く） | Supabase の資格情報が無くても開発・テストが回る。`@supabase/supabase-js` を入れずに済み、依存追加の規約を守れる | supabase-js を依存に追加（便利だが規約上は要相談） |
| ポイント更新の整合性 | Route Handler で純粋関数が新残高を計算し、`updateBalances` の compare-and-set で書く（不一致なら最大 3 回やり直し） | Supabase の RPC（PL/pgSQL）に計算を二重実装すると TS 側のテストと乖離する。同時アクセスは数十人規模なので CAS で十分 | Postgres 関数で全計算（原子性は高いがロジックが二重になる） |
| 実行委員ログインの代替 | Supabase 未設定時は `ADMIN_EMAIL` / `ADMIN_PASSWORD`（開発時のみ既定 `admin@example.com` / `admin`） | Supabase 無しでも管理画面の動作確認ができる。本番でどちらも未設定ならログイン不可 | — |
| 演出ライブラリ | 未導入。CSS keyframes（`steps()`）＋ WebAudio のビープ＋ Canvas 2D（的中演出の紙吹雪を直接描く）で実装 | 裏画面は「古い賭博端末」の世界観なので、液晶上のリール回転とビープ音で十分に成立する。依存を増やさない | Framer Motion / GSAP / Lottie / canvas-confetti / Howler.js（AGENTS.md の構成案。必要になれば相談して追加） |
| ホスティング | Vercel（無料枠） | Next.js との相性・自動デプロイ | GitHub Pages（サーバー処理ができないため不可） |
| ベット方式 | パリミュチュエル方式 | 「本場のカジノ・競馬に近いルール」という要望に合致し、運営側が損得のリスクを負わない | 固定オッズ方式（実装は簡単だが本格感で劣る） |
| ポイント計算の実行場所 | サーバー側（Supabase RPC/Route Handler） | クライアント側計算だと生徒による不正なポイント操作を防げない | クライアント計算（不可） |
| 借金の管理方法 | `points_balance` と `debt_amount` を分離管理するクレジット方式 | 「借りる」操作を明示的な体験にでき、本場のカジノのマーカー方式に近い演出ができる | 残高一本化（シンプルだが「借りた」実感が薄い） |
| UI/アニメーション | CSS keyframes ＋ WebAudio（モック v2・v3 の `om-*` キーフレームを移植）＋ Canvas 2D（紙吹雪。canvas-confetti は入れずに直接描く）。外部ライブラリは未導入 | 表画面「爆裂」と裏画面「古い賭博端末」で世界観を完全に切り替える。モックの演出は CSS だけで成立しているため、依存を増やさない | Framer Motion＋GSAP＋Lottie＋canvas-confetti＋Howler.js（必要になれば相談して追加） |
| デザイントークン管理 | `project-design-system` スキルで表画面・カジノ画面それぞれの `DESIGN.md` を作成 | 2つの世界観を一貫性を保ちながら実装するため、色・フォント・モーションをトークン化して固定する | その都度スタイルを決め打ち（一貫性が崩れやすい） |
